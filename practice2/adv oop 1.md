# Проект «Гибридное хранилище задач с подключаемыми бэкендами»

Постановка инженерной задачи. Нужно спроектировать библиотеку для управления задачами (Task) с возможностью хранить их в разных местах: в памяти, в JSON-файле, в SQLite. Библиотека должна позволять добавлять новые бэкенды без изменения ядра, гарантировать валидность данных, эффективно работать с большим количеством объектов и предоставлять чёткие контракты для интеграции.

## Техническое задание 
### Функциональные требования
|ID|	Требование|
|------|----------|
|FR-1|	Задача Task имеет поля: id (str, UUID4), title (str, 1–200 символов), status (todo / in_progress / done), created_at (datetime, UTC, timezone-aware), tags (list[str], по умолчанию пустой), priority (int, 1–5, по умолчанию 3)|
|FR-2|	Операции хранилища: save(task), get(task_id), delete(task_id), list_all(filter=None)|
|FR-3|	list_all поддерживает фильтрацию по TaskFilter: по статусу, по тегу, по минимальному приоритету; фильтры комбинируются по «И»|
|FR-4|	Минимум два бэкенда: InMemoryRepository и JsonFileRepository|
|FR-5|	Сторонний код должен иметь возможность подключить свой бэкенд, не импортируя нашу библиотеку и не наследуясь от наших классов|
|FR-6|	Ошибки: TaskNotFound, DuplicateTaskId, StorageError|

### Нефункциональные требования
|ID|	Требование|
|------|----------|
|NFR-1|	Ядро и тесты не должны зависеть от конкретной реализации хранилища|
|NFR-2|	Task неизменяем: после создания его поля нельзя переприсвоить|
|NFR-3|	Полные type hints, mypy --strict проходит без # type: ignore|
|NFR-4|	Для каждого бэкенда — одинаковый набор контрактных тестов|
|NFR-5|	Один и тот же экземпляр Task можно сохранить в двух разных бэкендах, и второй бэкенд не увидит «соседских» изменений|

## Анализ требований и проектирование контракта

Инженерный этап: требования → сущности → операции → инварианты → выбор механизма контракта.

### Задачи

1. Разбор ТЗ. Выписать в таблицу: сущность → какие у неё инварианты → какие операции над ней допустимы. Отдельно выписать, что является ошибкой предметной области (невалидный заголовок), а что — ошибкой инфраструктуры (битый JSON-файл). Это разные типы исключений, и путать их нельзя.

2. Контрактный документ. Написать docs/design-week1.md объёмом ~1 страница:

- перечень методов хранилища с сигнатурами и семантикой (что возвращает, что кидает, что гарантирует);

- список инвариантов Task;

- явное решение: какие операции идемпотентны (save существующего id — ошибка или upsert? зафиксируйте решение);

- что означает list_all(filter=None) — все задачи или пустой список.

3. Решение «ABC vs Protocol». Письменно ответить на 4 вопроса:

- Кто пишет реализации контракта: мы сами (внутренние бэкенды) или внешние разработчики?

- Нужна ли нам общая реализация в базовом классе (шаблонный метод)?

- Нужна ли проверка isinstance(x, BaseRepository) в рантайме?

- Должен ли внешний бэкенд тянуть импорт нашей библиотеки, чтобы считаться валидным?
